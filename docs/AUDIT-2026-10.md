## 二、🔴 P0 问题（9 项，全部已实测确认）

### P0-1 前端存储型 XSS + `javascript:` 协议注入（**最高危**）

**位置**：`web/static/js/pages/messages.js:52`（转义缺失）、`:152`/`:169`（协议白名单缺失）

**实测结论**：已用 Node 复现，输入 `<card title="x">通知\n<img src=x onerror="alert(1)">\n</card>` 经 `_renderCardBody` 输出**保留原始 `onerror`**。

三个叠加缺陷：
1. `_renderCardBody(cm[2].trim())` 收到的是**未经 escapeHtml 的原始消息体**（`:52`），而函数内 `:183/185` 直接把行交给 `_renderInline`；
2. `_renderInline`（`:192-199`）只做加粗/方括号替换，**不做任何转义**，函数注释却写"输入已 escapeHtml"——注释与实现不符；
3. `:181` 的 `!line.includes('<')` 守卫**恰好放行**含 `<` 的恶意行（本意是保护已渲染 `<a>`，副作用是放行攻击载荷）。

**协议白名单**：`escapeHtml`（`core/util.js:6-14`）只转义 `& < > " '`，**冒号与 ASCII 字母原样保留**，故 `href="javascript:alert(1)"` 可穿透 `:152`/`:169`。同文件 `_renderText`（`:209`）**已有正确防御** `if (!/^(https?:|mailto:)/i.test(cleanUrl)) return _match;`——只是卡片路径漏掉了。

**攻击链**：钉钉/飞书外部用户发一条带 `<card>` 的消息 → 管理员打开消息页 → 脚本执行 → 窃取 `core/api.js:82` 存在 `localStorage` 的 `jwt_token` → **账号接管**。

**修复**：
```js
// messages.js:52 —— 传入前转义
const body = _renderCardBody(escapeHtml(cm[2].trim()), imagePathMap);
// messages.js:152 / :169 —— 复用 :209 已有的协议白名单（提取为 core/util.js 的 safeUrl）
```
> 注：`_renderCardBody` 内部仍需保留 `renderImg` 的 HTML 注入能力，故推荐在**入口转义 + 内部对 placeholder 标记豁免**，而非全量转义后破坏图片渲染。

**预期收益**：消除账号接管路径。**这是本报告唯一"外部攻击者可直接利用管理台"的漏洞。**

### P0-2 登录接口 JSON 分支完全绕过爆破限流

**位置**：`web/api.py:653-681`

**实测结论**：逐行对比确认——Basic 分支（`:628-643`）完整调用 `_auth_rate_allowed(ip)` + `_auth_record_fail(ip)`；**JSON 分支（`:653-681`）两者都没有**，`_auth_check` 失败直接 `return 401`。

且 `/api/auth/login` 在 `_AUTH_WHITELIST`（`:288`）内，中间件限流不覆盖。`auth_middleware.login()` 内部虽有 `_login_rate_allowed`，但只在 `_auth_check` **通过后**才被调用（`:675`）——密码错误时已在 `:671` 返回，永远走不到。

**后果**：攻击者可用 JSON 体无限速爆破管理后台密码。这是 P0-3/P0-4 的放大器。

**修复**：JSON 分支补齐双维度（IP + 账号）限流，失败时 `_auth_record_fail` 记账。**约 8 行。**

### P0-3 生产密码明文存储 + PBKDF2 实现是死代码

**位置**：`web/api.py:376-381`（`_auth_check`）

`_auth_check` 用 `hmac.compare_digest` 直接比对**明文**。而 `web/auth_middleware.py:148-170` 完整实现了 `hash_password`/`verify_password`（PBKDF2-HMAC-SHA256、200k 轮、随机盐、恒定时间）——**质量很好，但从未接到主认证路径**（只被 `login()` 调用，而 `login()` 只在 `_auth_check` 通过后调用）。

**陷阱**：`config.yaml.example:725` 注释建议用户改用 PBKDF2，但改了会导致 `_auth_check` 恒 False → **服务完全无法登录** → 唯一出路是改回明文。文档指引事实上把部署推向明文。

**修复**：`_auth_check` 复用 `verify_password` → 迁移生产密码为 PBKDF2 → 消除双实现。

### P0-5 DB 初始化超时后"lazy-init 重试"是失效代码

**位置**：`src/platform/primary.py:148` + `src/memory/sqlite_store_conn.py:68-78`

**实测确认**：超时分支执行 `primary.store._schema_initialized = False`（**实例字段**），但 `conn` 门控已改为读**类级** `_schema_initialized_paths`（`:71-75`）。该路径只在 `sqlite3.Error` 时被 `discard`（`:102`），**超时路径不走异常分支** → `need_init` 恒为 `False` → `init_db()` 永不重试。实例字段 `_schema_initialized` 全仓**已无任何读取点**，是死变量。

**后果**：启动期 DB 初始化超时（磁盘慢/锁竞争）后 schema 永久不自愈 → `no such table` → **全接口 500**，与历史事故表现完全一致。日志却说"将 lazy-init 重试"，**误导排查**。

**为什么测试没抓到**：`tests/test_timeout_guard.py:157` 的 `_FakeStore` 只有实例属性、不实现类级集合，断言的正是被弃用的字段。

**修复**：`primary.py:148` 补 `type(primary.store)._schema_initialized_paths.discard(db_path)`；测试桩补类级集合。**约 2 行。**

### P0-6 LLM 流式请求从不传 `stream=True`，降级逻辑因生成器惰性完全失效

**位置**：`src/llm/client.py:787-794`（`_do_chat_stream`）、`:546-557`（`chat` 流式分支）

**PoC 实测输出**：
```
返回对象是生成器吗: generator
调用前已发出请求数: 0
迭代时才抛错: TypeError boom-network
实际请求 kwargs 是否含 stream=True: False  ← 只有 stream_options
```

两个缺陷：
1. 首次请求只加 `stream_options`，**没加 `stream=True`** → 服务端返回非流式对象 → 迭代时 `'_Resp' object is not iterable`；
2. `_do_chat_stream` 是生成器函数（实测 `inspect.isgeneratorfunction == True`），故 `chat()` 的 `try/except` 是**死代码**——异常在调用方迭代时才发生，已跳出 `try`。所谓"流式失败降级为非流式"**从未生效过**。

**后果**：配置 `stream_enabled: true`（`config.yaml:265`）时表现为"回复生成中断"。且 `tests/` 无任何 `_do_chat_stream` 用例。

**修复**：`create_kwargs["stream"] = True`；把生成器拆为「eager 建连 + 惰性迭代」两段使 `try/except` 真正覆盖建连；补回归测试。

### P0-7 全模型冷却期时 `raise None` → `TypeError`，掩盖真实错误

**位置**：`src/llm/client.py:576-590`

`state.last_err` 仅在 `_retry_primary_model` 的 except 里赋值。**全部模型处于冷却期时**，`chat()` 循环全部 `continue`，`_retry_primary_model` 从未被调用 → `last_err` 保持 `None` → `raise None` → `TypeError: exceptions must derive from BaseException`。

**触发条件完全现实**：一次限频风暴后 30 秒内的任何重入请求都会踩中——**恰是系统最需要优雅降级的时刻**。且 `agent_steps/reply.py:205` 的 `isinstance(e, LLMRateLimitExhaustedError)` 分支不会命中，错误分类彻底失效。

**修复**：`if state.last_err is None: raise LLMRateLimitExhaustedError(...)`。**约 5 行，止住崩溃。**
