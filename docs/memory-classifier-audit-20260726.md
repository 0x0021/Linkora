# 记忆自动分类算法审计报告

日期: 2026-07-26

## 1. 审计范围

- `src/memory/classifier.py` — 记忆范围自动分类 (classify_memory_scope, _score)
- `src/memory/memory_repo.py` — 记忆存储与召回 (recall, save)
- `src/platform/memory.py` — 自动记忆提取管线 (extract_and_save)
- `src/memory/schema.py` — memories 表结构 (scope 字段)

## 2. 发现清单

### 2.1 分类标签体系

| # | 严重度 | 问题描述 | 影响 |
|---|--------|---------|------|
| 1 | 🟢 低 | **仅有 personal/public 二分类**：标签体系过于粗粒度。无 topic 标签（如"团队规范"/"技术架构"/"人事信息"）、无 sentiment（正面/负面/中性）、无时效性标记。 | 召回时无法按主题过滤，所有 public 记忆混在一起 |
| 2 | 🟢 低 | **标签膨胀不适用**：当前只有 2 个标签，不存在相似标签合并的需求。但未来若扩展 tag 体系需关注。 | N/A |

### 2.2 分类器输入特征

| # | 严重度 | 问题描述 | 影响 |
|---|--------|---------|------|
| 1 | 🟡 中 | **纯子串匹配导致误匹配**：`_score()` 使用 `word in content` 做子串匹配。`API` 可匹配 "纸API机"、"部门"可匹配"非部门成员"、"我"可匹配"自我认知"。短词（1-3 字）尤其容易误匹配。 | 分类信号噪声大，可能将个人记忆误归为公共或反之 |
| 2 | 🟡 中 | **忽视消息长度信号**：长文本（>200字）更可能是团队规范/制度类公共知识，短文本更可能是随口一提的个人琐事。当前 `_score` 完全忽略长度。 | 长制度文本和个人简短对话无区分 |
| 3 | 🟢 低 | **忽视时间上下文**：同一发送者的近期记忆分类结果未用于调整当前记忆分类。若用户连续 3 条记忆都被归为个人，第 4 条"我下午请假"大概率也是个人。 | 缺少连续性先验 |
| 4 | 🟢 低 | **忽视来源信号权重差异**：`auto_extract`（LLM 自动提取）与 `manual`（用户手动添加）使用相同分类逻辑。手动添加时用户主动输入的内容更可能是有意分享的公共知识。 | 手动添加的公共知识可能被误归为个人 |

### 2.3 冷启动问题

| # | 严重度 | 问题描述 | 影响 |
|---|--------|---------|------|
| 1 | 🟢 低 | **新用户无历史时分类质量一致**：首次运行时的信号词库是写死的（PUBLIC_PATTERNS / PERSONAL_PATTERNS），不因用户或团队而异。但首次也有这些词库可用，并非完全冷启动。 | 影响极小——信号词库是静态但覆盖全面 |

### 2.4 置信度反馈

| # | 严重度 | 问题描述 | 影响 |
|---|--------|---------|------|
| 1 | 🟡 中 | **无置信度输出**：`classify_memory_scope` 返回确定性 (scope, reason)，无 confidence 分数。当 public_score=2.0、personal_score=1.9 时（刚过阈值），与 public_score=6.0、personal_score=0.0 的情况使用同一标记 "public"，但前者远不如后者可靠。 | 低置信分类无人工审核触发机制 |
| 2 | 🟢 低 | **分类失败无降级建议**：当 `classify_memory_scope` 因异常回退时，仅日志记录 debug，无向调用方返回 `"unknown"` 或 `"pending_review"` 等降级标签。好在异常路径已 try/except 并默认 personal。 | 已安全降级 |

### 2.5 性能优化

| # | 严重度 | 问题描述 | 影响 |
|---|--------|---------|------|
| 1 | 🟢 低 | **无缓存**：每次调用 `_score()` 遍历全部 PUBLIC_PATTERNS + PERSONAL_PATTERNS（共约 140 条），做简单子串匹配。列表遍历 O(n*l) 每调用约 0.1ms，对于 < QPS 10/L2 的查询量不构成瓶颈。 | 性能无实际影响 |

## 3. 已实施的改进

### 3.1 词边界匹配（防子串误匹配）

为长度 ≤ 2 的短中文关键词（如"他"、"她"、"我"、"咱"）和 ≤ 3 字符的 ASCII 英文关键词（如"API"、"KPI"、"OKR"）增加词边界正则匹配：

- "API" 能匹配 "调用 API 接口" 但不能匹配 "纸API机"
- "他" 能匹配 "告诉他" 但不能匹配 "其他"
- 长词（≥3 字中文，如"工资""产品"）保留原子串匹配（误匹配概率极低）

### 3.2 分类置信度输出

`classify_memory_scope` 返回三元组增加 `confidence` (0.0~1.0)：

- `public_score - personal_score >= 4.0` → confidence = 1.0（高置信）
- `public_score - personal_score < 1.0`（含刚过阈值）→ confidence = 0.5（低置信，边界 case）
- 中间档 → confidence = 0.7~0.9
- 显式指定 → confidence = 1.0

### 3.3 内容长度信号

在 `_score` 中增加长度得分：
- 内容 > 200 字符 → public_score + 0.5（长文本更可能是制度/规范）
- 内容 < 20 字符 → personal_score + 0.3（极短文本更可能是随口一提）

### 3.4 来源信号权重

- `source` 为 `auto_extract`（LLM 自动提取）→ 不加权（保持原有逻辑）
- `source` 为 `manual` 且无 `sender_id` → 已按规则 1 直接判定为 public（不变）
- `source` 为 `manual` 且有 `sender_id` → personal_score + 0.3（用户对着某人说的事更可能是个人）

## 4. 标记为建议的高风险改动

| # | 建议 | 风险 |
|---|------|------|
| 1 | 引入多标签 topic 分类（如 team_norm/tech/travel/hr） | 🟡 需要训练分类器或 prompt engineering，增加 LLM 调用成本 |
| 2 | 基于用户记忆历史实现个性化阈值 | 🟡 需要跟踪每个用户的分类历史，增加存储复杂度 |
| 3 | 用 embedding 相似度替代关键词打分 | 🟡 每条记忆需做 embedding，延迟增加 50-200ms |
| 4 | 低置信分类触发人工审核 | 🔴 需要设计和实现审核 UI 与管理流程 |

## 5. 结论

记忆分类算法设计简洁有效，满足当前需求。主要改进方向：
1. 词边界匹配防误匹配（已实施）
2. 置信度输出以支持下游差异化处理（已实施）
3. 多维度特征（长度、来源）提升准确性（已实施）
4. 未来可考虑 topic 标签扩展以支持更精细的召回过滤
